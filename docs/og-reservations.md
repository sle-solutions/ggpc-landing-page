# Shared checkout reservations, private proposal

This local change is not deployed or activated. It issues no codes, adds no coupon UI and sends no member messages. It uses the existing secret-authenticated Apps Script transport and existing Orders tab. No new database, service, key or timer is introduced. The pricing config, fee calculation, first-100 eligibility, frozen OG physical order and waitlist fallback remain the authority.

Root's read-only 6 November reconciliation found no OG tab and no Orders data rows (43 existing headers), so the smallest foundation is one appended `Checkout claim` cell per existing Orders row, rather than creating/filling an OG tab or operating the offline SQLite prototype as a second ledger. The proposed header is column 44; all original positions remain unchanged. The JSON stores version, immutable member/order identity, checkout intent/quote binding, OG decision, original creation time, held/consumed state, provider IDs and bounded event receipts. It contains no raw coupon code. Manual Notes/QA/actuals are never rewritten during existing-row updates, even from stale projections.

## Protocol

- The browser creates one random checkout-intent UUID for the current tab's selection/email. A failed HTTP request or repeated click reuses it. Explicit form changes create another intent, but cannot bypass an existing OG hold. Reloading the tab loses this local reference; it does not release a hold. Recovery then requires the existing operator process, not an automatically adopted new intent.
- The server re-quotes and hashes exact selection, price/fee lines, lane, email, add-ons and site into a binding. Observation ages/timestamps are excluded. The first accepted human Parts text and Prices checked value remain an immutable freshness snapshot: a claim retains the original Parts snapshot for storage-integrity checks, while replay checks the economic/identity/provider binding independently of later seenAgo minute/hour/day buckets. Replays do not relabel the old snapshot as fresh. Apps Script's `checkout_reserve` serializes every legacy OG checkout under ScriptLock, re-reads the same membership/use authority, and durably writes the order/hold before returning an OG decision. An exact intent/binding replay returns its ORIGINAL order ID. A competing held intent or changed binding refuses; no silent full-price fallback for unknown holds. A previously consumed member may make a later ordinary full-price order, matching existing behavior.
- Old `og_check` is informational inside a failed `reservation_required` protocol response. Old websites fail closed rather than authorize a discounted session or silently charge an OG member full price from an uncoordinated check. The website has no `ogCheck -> og:true` authorization path. Old `order_upsert` cannot create an OG-applied order or mutate a managed claim; it also cannot erase a legacy OG flag or change that row's original member email.
- Stripe creation uses the stable original order's idempotency key. The exact returned session is attached and read back before returning its URL. Lost create/attach responses keep the hold. Exact retries can recover the same provider session within a conservative 20-hour provider-idempotency retry horizon; that horizon is NOT an entitlement expiry and never releases a member. After it, automated creation refuses and requires operator/provider reconciliation rather than risking reuse after provider key retention.
- Signature-verified webhooks carry immutable intent/binding metadata on both Session and PaymentIntent. Apps Script checks original claim/order/session/payment-intent/event binding. Authorized/paid consumes monotonically, independent of mutable billing/contact email. Cancellation, expiry, refund-looking status and elapsed time never restore eligibility. Same-event replay repairs interrupted owned-field writes. A duplicate Session event may observe the same PaymentIntent after capture; authorized/paid observations with the same provider IDs both consume once and can advance the physical order to paid without another event receipt. Conflicting event/provider identity refuses. Relevant event receipts are bounded to 32 entries per claim, below cell-size limits; overflow holds for review rather than forgetting dedupe history.
- A claim write precedes remaining owned-field writes on an existing row. Failed writes/readbacks do not report success. Unknown outcomes are retained; duplicate events repair rather than blindly repeating a benefit. There is no claim release endpoint and no inferred no-session proof. All provider network calls, including existing order-alert sends, run outside ScriptLock. Lock-held helpers never nest locks.

## Preconditions and unresolved behavior

Before any remote integration, root must re-read/backup/verify the exact workbook and deployed nonsecret script, reconcile original member/use/session identities, inspect proposed append-only column 44, and coordinate Apps Script plus website protocol cutover while checkout remains unavailable. A legitimate update of a previously authorized/paid legacy OG row first persists a `legacy-consumed` proof in the same claim column, with original member/order, observed positive status and timestamp. The proof precedes any status downgrade, is immutable on replay and preserves later full-price purchasing without another perk. An already-canceled legacy row with no known positive evidence stays held; no consumption or release evidence is invented. Known legacy header lengths are recognized; other shapes, malformed claims, duplicate identities or ambiguous membership stop reservation. No automatic data repair, re-freeze, code issuance or remote schema edit is included here.

The current source's first-100 rule is retained: existing OG physical email order if present, otherwise First joined with original row order as tie-break. Strict shape/date/duplicate checks fail closed on ambiguous future inputs instead of silently re-ranking. Numeric frozen Rank does not replace physical order. Root reported all35 reconciled members retained with no normalized duplicates/malformed emails/First joined ties, and no existing Orders or OG rows. These are root's private reconciliation facts, not a new row read by this implementation leaf. Root separately observed two non-membership Picks made cells with date/display coercion; that anomaly is recorded only and is not repaired or used for eligibility here.

Historically canceled/expired/old checkout rows may have had a prior authorization or unknown session. They remain held until separately reviewed. A known authorized/paid row remains consumed; mutable historical email ambiguity is not guessed. No refund/exception policy, bank-transfer policy, manual quote commitment stage, mailbox-ownership rule or consultation workflow is invented. Current quote requests do not consume an entitlement. A future policy-supported release must prove the exact provider outcome and preserve any consumed evidence; it requires a separate reviewed change.

There is no anonymous UI for hold recovery and no automatic release/retry job. The error copy says checkout could not be confirmed and advises retrying the same details or contacting GG PC before starting another order. It never claims nothing was charged after an unknown provider/storage outcome. The existing labour floor and fee-only discount are unchanged. Local tests are synthetic and do not certify Apps Script cloud atomicity or a live Stripe account. Real controlled integration/cutover, code integration, activation, distribution, Store/public release and all sends remain separately gated.
